Phase 0.2 — Architecture

The 6GB Interview Loop

Every model in this project shares one 6GB laptop GPU. That constraint — not preference — is what decides which stages run sequentially, one blocking the next, which run in parallel, off the critical path, and which can't coexist in memory at all. This is that design, stage by stage.

00 · Setup — runs once

Parse and embed run together; planning waits

Parsing the resume and embedding it for retrieval both only need the raw resume text, so they run in parallel — Parser is a cloud call (Groq), Embedder is a small local model, neither blocks the other. Planning is different: it needs Parser's structured output (skills, experience) to build a sensible question sequence, so it waits for Parser specifically, not for Embedder.

01 · Live turn loop — repeats every question

One blocking chain, one thing always listening

Six stages happen in strict sequence — each one waits for the last, because each needs the previous stage's output to exist: no transcript, no answer; no answer, no audio; no audio, no lip-sync. VAD is the exception — it never stops listening, including while the avatar is mid-playback, which is what lets a candidate interrupt instead of waiting out a reply they've already understood.

Why the sequencing above isn't a choice

The whole design answers to 5.9GB free

The Interviewer LLM stays resident the entire session (keep_alive: -1) to avoid an 15-20s reload between turns — so it permanently claims its share of the card. Everything else in the live loop has to fit in what's left. That's the real reason Wav2Lip exists as a fallback, and the real reason Planner can't run mid-interview.

02 · Post-interview — runs once

Scoring costs nothing on this GPU

Once the last turn ends, the transcript goes to gpt-oss-20b on Groq for rubric scoring. It's cloud-hosted and fully asynchronous — there's no live turn waiting on it, and it draws nothing from the 6GB budget the rest of this document is built around.
